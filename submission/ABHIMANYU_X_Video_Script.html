Every autonomous patch tool has the same problem: the AI that writes the fix is the same AI you're asking to grade its own homework.

ABHIMANYU X doesn't do that. Here's what it actually does, end to end, against a real vulnerable C program — no staged demo, no mocked steps.

01What This Is30–40s
▦
ScreenREADME header, or the Mission Dossier hero section — "AI proposes → Evidence decides → Verification proves → Memory learns."

This is ABHIMANYU X — an autonomous cyber-reasoning and self-repair system, built for the AI Kavach Challenge.

The brief asks for a system that's an LLM laced with fuzzers, static and dynamic analysis, and a regression harness — one that finds a vulnerability, patches it, and proves the fix holds. Not "generates a plausible-looking diff." Proves it.

The core idea in one line: AI proposes, evidence decides, verification proves, memory learns. The LLM's output is never trusted by default — it's just a proposal. An independent verification engine, running real compiles and real exploit replays, is what actually decides whether a patch is good.

02The Architecture, Briefly30soptional
▦
ScreenREADME architecture diagram, or scroll through the Mission Dossier's "Deep System Architecture" section.

Under the hood: a Mission Engine drives the whole lifecycle. Every compile, every exploit replay, every fuzzing run happens inside an isolated Colima Linux VM — never on the host machine. Discovery feeds an evidence bundle to a local LLM called ANVIL. ANVIL's patch goes through an independent verification chamber. Only if it passes does anything get written to Immune Memory.

If it fails, the failure reason goes back to ANVIL for a second attempt — bounded at two tries, not an unbounded loop.

04ANVIL Reasons About It20–30s — real dwell time, let it breathe
▦
ScreenSide by side — ANVIL panel on one side (Provider: local, Model: qwen2.5-coder:3b), the vulnerable source code on the other.

Now the system slows down for real — because this is genuine local inference, not an instant canned response.

ANVIL is a small model, Qwen2.5-Coder 3B, running entirely on this machine through Ollama. Nothing about this vulnerability, this code, or this patch ever leaves the host. It reads the full vulnerable file — not a snippet — and reasons about root cause before writing a single line of patch.

This step alone typically takes somewhere between twenty seconds and just over a minute, depending on how loaded the machine is. That's the honest range, measured across multiple real runs — not a fixed number. It's the slowest part of the whole mission by far, and it's the part most people would assume is instant.

06Verification — Where Trust Actually Gets Earned20–25s
▦
ScreenVerification Chamber panel — gate list ticking to 8/8, before/after ASan crash replay box.

This is the part that matters most, and it's the part most "AI auto-patch" demos skip.

Eight independent, real gates. The patch has to actually compile. The real crash input — the one AFL++ found — gets replayed against the patched binary inside the VM, live. It has to genuinely reject the malicious input, not just look like it does.

Then it's compiled a second time, completely separately, under UndefinedBehaviorSanitizer — a different instrumentation catching a different bug class than AddressSanitizer. Regression and behavior checks confirm nothing else broke. And then — only for patches that already passed — an adversarial sweep replays six more payload sizes the original crash never touched, to catch a patch that just memorized one input instead of fixing the actual bug.

Eight for eight. Verified.

Not a fabricated "memory helps" story. A single real trial each way, both independently verified the same eight-gate way as before.

// Notes for whoever records this

  • Don't fake the ANVIL wait. Either let it run real-time with b-roll (architecture diagram, code scroll) over it, or cut to it having just finished — don't speed it up in a way that implies it's instant. The honest range is ~20s–70s+ per call, measured across real runs this session (fastest recorded: 22.6s total mission; slowest recorded: 73s for ANVIL alone).
  • Transfer's result is not scripted. Read whatever the WITHOUT/WITH MEMORY panels actually say when you record — don't narrate an assumed outcome.
  • The Provenance values above are from one specific real run (2026-08-30, mission ABX-20260830-143427). Quote your own run's numbers when you actually record, not these — that's the entire point of the panel.
  • Every on-screen badge (MEASURED / AI-GENERATED / DEMO / FUTURE) is real UI, not something to paraphrase away — if you're narrating over a DEMO-labeled figure (e.g. AFL++ executions/sec, coverage %), say so explicitly, the same way the UI does.
